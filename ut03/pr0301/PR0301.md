## 1. Diseño de la Capa Bronce

### 1.1. Enfoque elegido

Para el laboratorio se ha optado por un **Single-Bucket** con prefijos, ya que
el enunciado pide un único bucket `datalake-turismo-bronce-<iniciales>`. En un
entorno de producción se separarían las capas en buckets independientes
(Multi-Bucket).

La Capa Bronce conserva los datos **en su formato original**, sin transformar.
Se distinguen dos tipos de contenido:

- **Catálogos maestros estáticos:** se separan por proveedor y se versionan con
  `v1/` para poder mantener trazabilidad si MITECO o AEMET cambian su estructura.
- **Predicciones meteorológicas:** son eventos diarios y se particionan al estilo
  Hive por fecha de ingesta (`year=YYYY/month=MM/day=DD/`), lo que permitirá a
  Athena o Spark aplicar *partition pruning* en fases posteriores.

### 1.2. Jerarquía de claves en S3

```text
s3://datalake-turismo-bronce-<iniciales>/
└── bronce/
    ├── catalogos/
    │   ├── miteco_playas/
    │   │   └── v1/
    │   │       └── playas.csv
    │   └── aemet_codigos/
    │       └── v1/
    │           └── playas_codigos.csv
    └── meteorologia/
        └── aemet_prediccion_playas/
            └── year=YYYY/
                └── month=MM/
                    └── day=DD/
                        ├── pred_playa_0301101_101530.json
                        └── ...
```

## 2. Exploración y cruce de los catálogos

### 2.1. Codificación y separador

| Fichero | Proveedor | Separador | Codificación | Filas |
|---|---|---|---|---|
| `data/playas.csv` | MITECO | `,` | UTF-8 con BOM | 3.554 |
| `data/playas_codigos.csv` | AEMET | `;` | ISO-8859-1 / cp1252 | 591 |

La lectura correcta requiere indicar explícitamente `encoding` y `sep`; de lo
contrario aparecen caracteres corruptos en los nombres con tildes o eñes.

### 2.2. Clave de unión

El nexo entre ambos catálogos es el **código INE del municipio**:

- MITECO: columna `Código_IN` (5 dígitos).
- AEMET: columna `ID_MUNICIPIO` (5 dígitos).

`ID_PLAYA` es un identificador interno de AEMET de 7 dígitos y **no** coincide
con `Identifica` de MITECO. Solo se utiliza para consultar la API.

Ambos códigos se normalizan con `zfill` para conservar los ceros a la izquierda
(`3018` → `03018`, `301101` → `0301101`).

## 3. Consumo de la API de AEMET

La API de AEMET OpenData utiliza un flujo de **doble salto**:

1. `GET https://opendata.aemet.es/opendata/api/prediccion/especifica/playa/{ID_PLAYA}`
   con la cabecera `api_key`. Devuelve un JSON de control con el campo `datos`
   (URL temporal).
2. `GET` a esa URL temporal para descargar el JSON final de predicción.

El cliente `src/aemet_client.py`:

- Valida que `ID_PLAYA` tenga 7 dígitos.
- Controla HTTP 404, 429, timeouts y errores de conexión.
- Registra un `WARNING` y devuelve `None` sin detener el pipeline.
- Aplica `time.sleep(1.5)` después de cada llamada para respetar el *rate limit*.
- Decodifica el JSON probando UTF-8 e ISO-8859-15/cp1252 para conservar tildes
  y eñes.

Prueba real realizada con `ID_PLAYA = 0301101` (Raco de l'Albir): la API
devolvió una lista JSON de 2.394 caracteres con los textos correctamente
codificados (`España`, `débil`, `predicción`, etc.).

## 4. Ingesta en Amazon S3

### 4.1. Creación del bucket

El pipeline crea el bucket mediante `boto3` si no existe
(`crear_bucket_si_no_existe`). Se valida el nombre y se tiene en cuenta la
región: en `us-east-1` no se envía `CreateBucketConfiguration`; en el resto de
regiones sí.

### 4.2. Subida de ficheros y de datos en memoria

Se han implementado las dos modalidades:

- `upload_file`: sube los dos catálogos CSV desde disco local.
- `put_object`: sube el JSON de cada predicción directamente desde memoria RAM.

Todos los objetos incluyen metadatos nativos de trazabilidad:

```json
{
  "source": "MITECO_OpenData | AEMET_Catalogo | AEMET_API",
  "ingestion_timestamp": "YYYY-MM-DDTHH:MM:SSZ"
}
```

Ejemplo de verificación con `head_object`:

```text
Key: bronce/catalogos/miteco_playas/v1/playas.csv
Metadata: {
  "source": "MITECO_OpenData",
  "ingestion_timestamp": "2026-11-23T10:15:30Z"
}
```

> un objeto (`capturas/02_s3_bucket.png` y `capturas/03_s3_metadata.png`).

### 5.1. Requisitos

```powershell

.\.venv\Scripts\Activate.ps1
pip install -r requirements.txt

# Solo si vas a ejecutar el cuaderno dentro de este entorno:

```

Crear un `.env` a partir de `.env.example` y rellenar:

```text
AWS_ACCESS_KEY_ID=...
AWS_SECRET_ACCESS_KEY=...
AWS_SESSION_TOKEN=...
AWS_DEFAULT_REGION=us-east-1
S3_BUCKET_NAME=datalake-turismo-bronce-<iniciales>
AEMET_API_KEY=...
```

> Las credenciales de AWS Academy son temporales (3-4 horas). Hay que
> actualizar el `.env` cada día de trabajo.
>
> **Error típico:** `HeadBucket ... 400 Bad Request` o `InvalidToken` suele
> indicar que las credenciales del `.env` están truncadas o son las de ejemplo.
> Longitudes esperadas: `AWS_ACCESS_KEY_ID` = 20 caracteres,
> `AWS_SECRET_ACCESS_KEY` = 40 caracteres y `AWS_SESSION_TOKEN` = una cadena
> larga (cientos o miles de caracteres). Copia el bloque completo desde
> **AWS Details → Show**.

## 7. Conclusiones

- La Capa Bronce debe conservar el formato original y separar los catálogos
  estáticos (versionados) de los eventos diarios (particionados por fecha).
- El particionado Hive `year=/month=/day=` facilitará el *partition pruning* en
  Athena o Spark.
- El cruce entre MITECO y AEMET debe hacerse por código INE, no por los
  identificadores internos de cada organismo.
- Las diferencias de codificación y separador entre los CSV son un riesgo real
  de corrupción de datos; se han tratado explícitamente.
- La API de AEMET requiere doble petición, control de códigos HTTP y una pausa
  entre llamadas para no superar la cuota.
- Los metadatos `source` e `ingestion_timestamp` permiten auditar el origen y
  el momento de cada objeto almacenado.
